## PART 1. 제품 정의

### 1.1 포지셔닝 재정의

원본의 한 줄 정의는 계산기에 머문다. 계산기는 이미 많고 이탈이 빠르다.

> **"내가 일한 걸 아무도 부정할 수 없게 만든다."**
> 부제(사용자용): 오늘 어디서 몇 시간 일했는지만 누르면, 이번 달 받을 돈이 나온다.

계산은 **미끼**이고, 실제 제품은 **근로자 본인이 만든 일별 원장(原帳)**이다. 임금 체불·시급 축소·근무시간 누락 분쟁에서 근로자가 가진 유일한 반대 증거가 이 기록이다.

이 포지셔닝이 만드는 설계상 귀결:
- 기록의 **작성 시점**이 신뢰성을 만든다 → `createdAt`은 절대 수정 불가, 사후 수정은 이력으로 남긴다
- **못 받은 돈**을 추적하지 않으면 증거 앱이 아니다 → C4
- 내보내기는 Phase 3가 아니라 **Phase 1에 최소형이 들어가야 한다** (아래 3.3 참조)

### 1.2 북극성 지표 (North Star)

| 구분 | 지표 | 목표 (출시 90일) |
|---|---|---|
| **North Star** | **주 3일 이상 기록한 주간 활성 사용자 (W3+ WAU)** | 300명 |
| 선행지표 1 | 첫 방문 → 첫 기록 저장 전환율 | 60% 이상 |
| 선행지표 2 | 홈 화면 추가(PWA 설치) 비율 | 30% 이상 |
| 선행지표 3 | 4주차 잔존율 | 35% 이상 |
| 반증지표 | 언어 선택 후 첫 기록 없이 이탈 | 20% 미만 |

*수집 방식*: Phase 1은 서버가 없으므로 로컬 카운터 + 익명 집계 핑(설치·첫기록·주간활성만, PII 없음). 이것도 부담이면 Plausible/Umami 같은 쿠키리스 분석 1종만. **개인정보 미수집 원칙은 유지한다.**

### 1.3 타겟 사용자 (재정의)

| 세그먼트 | 비자 | 특성 | 우선순위 |
|---|---|---|---|
| **A. 인력사무소 일용직** | E-9 이탈자, F-4, H-2, (미등록 포함) | 근무지가 매일 바뀜, 3.3% 공제, 현금·주급, 체불 위험 최고 | **1순위 (MVP 타겟)** |
| B. 제조업 상용 근로자 | E-9, E-7 | 근무지 고정, 4대보험, 연장·야간 많음 | 2순위 |
| C. 동포 건설·서비스 | H-2, F-4 | 한국어 일부 가능, 일당 단위 | 2순위 |
| D. 유학생 시간제 | D-2, D-4 | 주 20시간 제한, 카페·식당 | 3순위 (Phase 3) |

**A를 1순위로 잡는 이유**: 근무지가 매일 바뀌므로 기록 필요성이 가장 절박하고, 계산이 가장 어렵고(현장마다 시급·공제 다름), 체불 노출이 가장 크다. 원본의 "근무지 카드" 설계는 정확히 A를 겨냥한 것이다. **B는 근무지가 하나라 계산기 없이도 살고, 그래서 리텐션이 약하다.**

## PART 2. 도메인 규칙 정본 (개발 시 이 절이 유일한 진실)

### 2.1 연도별 상수 테이블

원본의 하드코딩 상수를 폐기하고 **발효일 기준 조회 테이블**로 만든다. 과거 기록은 그 날짜의 상수로 계산되어야 한다.

```ts
// /lib/payroll/rates.ts
export const MINIMUM_WAGE = [
  { from: '2024-01-01', hourly:  9860 },
  { from: '2025-01-01', hourly: 10030 },
  { from: '2026-01-01', hourly: 10320 },
] as const

export const INSURANCE_RATES = [
  {
    from: '2025-01-01',
    pension:      0.045,    // 국민연금 근로자 부담
    health:       0.03545,  // 건강보험 근로자 부담
    longTermCare: 0.1295,   // ⚠️ 건강보험료에 곱한다 (임금이 아님) → 임금 대비 ≈0.459%
    employment:   0.009,    // 고용보험 실업급여 근로자 부담
  },
  // 2026-01-01 요율은 확정 후 추가. 미확정 시 직전 연도 값을 사용하고 UI에 '잠정' 배지
] as const

export const DAILY_TAX = {
  dailyDeduction: 150_000,  // 일용근로소득 일 공제액
  rate:           0.06,     // 기본세율
  taxCredit:      0.55,     // 근로소득세액공제 55%
  localTaxRate:   0.10,     // 지방소득세 = 소득세의 10%
  minCollect:     1_000,    // 소액부징수 기준
} as const
```

> ⚠️ **법령 확인 필요 항목**: 위 수치는 2025년 기준 공개 요율에 근거한 정리다. 출시 전 노무사 또는 근로복지공단·건강보험공단 고시로 **반드시 재확인**하고, 확인 일자를 코드 주석에 남긴다. 잘못된 요율은 사용자의 임금 오해로 직결된다.

### 2.2 공제 방식 — 4종으로 확장 (C1, C2, C5)

원본의 3종은 실제 사례를 못 덮는다.

| ID | 사용자 문구 (ko) | 계산 | 대상 |
|---|---|---|---|
| `RATE_3_3` | "3.3% 떼는 곳" | 세전 × 3.3% | 인력사무소 사업소득 처리. **가장 흔함** |
| `DAILY_WORKER` | "일용직으로 신고하는 곳" | `max(0, (일급 − 150,000)) × 6% × 45%` + 지방세 10%, 1,000원 미만은 0 | 정식 일용근로자 신고. **일당 15만원 이하면 세금 0원** |
| `INSURANCE_4` | "4대보험 내는 곳" | 아래 2.3 | 정식 근로계약 |
| `NONE` | "전액 받는 곳" | 0 | 현금 일당 |

**추가 공제 (근무지별, 선택)**
```
otherDeductions: [
  { type: 'AGENCY_FEE',  label: '소개비',  mode: 'PER_DAY' | 'RATE', value: number },
  { type: 'DORM',        label: '숙소비',  mode: 'PER_MONTH', value: number },
  { type: 'MEAL',        label: '식대',    mode: 'PER_DAY',   value: number },
  { type: 'TRANSPORT',   label: '차비',    mode: 'PER_DAY',   value: number },
  { type: 'CUSTOM',      label: string,    mode: ...,         value: number },
]
```
소개비는 일당의 8~10%를 떼는 경우가 흔하다. 이걸 빼면 앱 금액과 실제 봉투 금액이 안 맞고, **사용자는 앱을 틀렸다고 판단하고 떠난다.**

> 💡 부수 효과: 소개비·숙소비 공제는 근로기준법상 임금 전액지급 원칙(제43조) 위반 소지가 있다. 앱이 이 금액을 **별도 항목으로 누적 표시**하면 그 자체가 상담·진정의 근거가 된다. Phase 3 노동권리 안내와 연결.

### 2.3 4대보험 — 국적별 국민연금 분기 (C2)

```
국민연금: 사회보장협정·상호주의에 따라 적용제외 국적이 존재한다.
  → 근무지 설정이 아니라 사용자 프로필의 '국적'으로 판정
  → 적용제외 시 공제율 ≈ 9.40% − 4.5% = 4.90%
고용보험: E-9(고용허가제)은 실업급여 임의가입 → 미가입 시 0.9% 제외
건강보험: 원칙적으로 의무 가입
```

**구현 방식**: 국적 하드코딩 리스트를 코드에 박지 않는다. 대신 근무지 설정에 3개 체크박스를 둔다.

```
[✓] 국민연금 떼요   [✓] 건강보험 떼요   [ ] 고용보험 떼요
   → 예상 공제율 4.90% 로 자동 갱신 (실시간 표시)
```

사용자는 자기 급여명세서를 보고 체크만 하면 된다. 법령 해석 리스크를 앱이 지지 않으면서 정확도는 올라간다. 온보딩 시 국적을 물어 **기본 체크 상태만 추천**한다.

### 2.4 5인 미만 사업장 (C3)

근무지 필드 `isUnder5Employees: boolean` 추가.

```
isUnder5Employees === true 인 경우:
  - 연장근로 배율 1.5 → 1.0
  - 휴일근로 배율 1.5 → 1.0, 휴일 8h 초과 2.0 → 1.0
  - 야간 가산 0.5 → 0
  - 계산 결과 화면에 안내 배지: "5인 미만 사업장은 가산수당 의무가 없어요"
```

UI 문구(ko): **"같이 일하는 사람이 5명보다 적어요"** — '상시근로자 5인 미만 사업장'이라는 표현은 한국인도 어렵다.

### 2.5 하루 계산 절차 (확정)

```
0) 적용 상수 = 해당 date의 최저임금/요율 테이블 조회
   시급 = workLog.hourlyWageSnapshot  (근무지 현재 시급이 아님 — 절대 원칙)

1) 실근로분 = elapsed(start, end) − breakMinutes
     end < start 이면 +24h (자정 넘김)
     시각 미입력이면 totalMinutes − breakMinutes 사용
   ⚠️ 실근로분 < 0 이면 저장 차단 + "휴게시간이 근무시간보다 길어요" 안내

2) 구간 분해
   [평일 & 5인이상]  기본 = min(실근로, 480분) ×1.0 / 연장 = 초과분 ×1.5
   [휴일 & 5인이상]  휴일 = min(실근로, 480분) ×1.5 / 휴일초과 = 초과분 ×2.0
   [5인미만]         전체 ×1.0

3) 야간 가산 (nightPayEnabled && 5인이상 && 시각 입력 있음)
   22:00~06:00 교집합 분 × 0.5 를 별도 구간으로 추가 합산
   ※ 연장+야간이 겹치면 1.5 + 0.5 = 2.0 이 되는 것이 정상이다
   ※ 22:00 정각 시작은 야간에 포함, 06:00 정각 종료는 미포함 (반개구간 [22:00, 06:00))

4) 일급(세전) = Σ(구간분 / 60 × 시급 × 배율), 원 단위 반올림 (Math.round)
   ⚠️ 반올림은 일급 단위 1회만. 구간별 반올림 후 합산 금지 (누적 오차)

5) 일별 공제 (DAILY_WORKER, PER_DAY 기타공제) 는 이 단계에서 계산해 별도 필드 보관
```

### 2.6 월 정산 절차 (확정)

```
월 세전합계   = Σ 일급
법정공제      = 방식별 계산
                RATE_3_3     : 월세전 × 3.3%
                DAILY_WORKER : Σ 일별세액 (일 단위로 계산해 합산 — 월합산 후 계산 금지)
                INSURANCE_4  : 월세전 × (체크된 보험 요율 합)
                NONE         : 0
기타공제      = Σ(PER_DAY × 근무일수) + Σ(PER_MONTH) + Σ(RATE × 월세전)
실수령 예상   = 월세전 − 법정공제 − 기타공제
미수금        = Σ(paymentStatus !== 'PAID' 인 일급)   ← 신규
```

| T12 | 동일 세전, 국민연금 제외 | 4.904% → 공제 80,975 / 실수령 **1,570,225원** |
| T13 | 시급 인상 후 과거 기록 조회 | 금액 불변 (스냅샷 검증) |
| T14 | 같은 날 A공장 4h + B공장 5h | 2건 저장, 일 합계 정상 |

**T4에서 드러난 미결 규칙 — 휴게시간을 어느 구간에서 뺄 것인가**

원본에 정의가 없다. 확정한다:
```
휴게시간은 근무 구간의 '중앙'에서 차감한 것으로 간주하지 않는다.
→ 야간 판정용 타임라인에서는 휴게를 '근무 종료 직전'이 아니라
  시간 비례(pro-rata)로 전 구간에 균등 차감한다.
  야간분 = round(원야간분 × (실근로분 / 경과분))
이유: 실제 휴게 시각을 사용자가 입력하게 하면 3탭 원칙이 깨진다.
      비례 배분이 어느 한쪽으로 체계적으로 유리/불리하지 않다.
      계산 결과 하단에 "휴게시간은 균등하게 나눠 계산했어요" 1줄 고지.
```

### 3.2 불변 규칙 (코드 리뷰 시 체크)

1. `hourlyWageSnapshot`은 WorkLog 생성 시 1회 기록. **어떤 경로로도 근무지 현재 시급을 참조하지 않는다.**
2. `createdAt`은 어떤 업데이트 경로에서도 갱신하지 않는다.
3. 근무지는 **삭제 불가**, `isArchived`만 가능. (외래키 무결성 + 증거 보존)
4. 스키마 변경 시 Dexie `version(n).upgrade()`를 반드시 작성한다. 로컬 우선 앱에서 마이그레이션 실패 = **사용자 데이터 영구 소실**이며 복구 수단이 없다.
5. 모든 금액 필드는 원 단위 정수. 부동소수 금지.

### 3.3 Phase 1에 내보내기 최소형을 넣는 이유

원본은 내보내기를 Phase 3에 뒀다. 하지만 **기기 고장·분실 시 로컬 전용 앱은 모든 증거가 사라진다.** Phase 2 동기화 전까지 사용자를 무방비로 두는 것은 제품 약속과 모순된다.

→ **Phase 1-D에 "전체 기록 JSON 내보내기/가져오기" 1개만 넣는다.** 버튼 1개, 파일 다운로드, 파일 선택 복원. 반나절 작업이고 데이터 소실 리스크를 없앤다. 예쁜 PDF·이미지 출력은 Phase 3 그대로.

## PART 4. 다국어 전략 (C6)

### 4.1 Phase 1 언어 재선정

원본 11개 언어에는 **일본어·힌디어·카자흐어·라오어**가 있고 **캄보디아어·인도네시아어·미얀마어·타갈로그어**가 없다. 국내 외국인 근로자 구성과 맞지 않는다. E-9 고용허가제 송출국 및 체류 규모를 기준으로 재배치한다.

| Phase | 언어 | 근거 |
|---|---|---|
| **1 (6개)** | `ko` `en` `vi` `km` `ne` `id` | ko=기준, en=폴백, 베트남·캄보디아·네팔·인도네시아 = E-9 최대 송출국군 |
| **2 (+5개)** | `my` `th` `zh-CN` `ru` `uz` | 미얀마·태국 / 중국동포(H-2) / 고려인·중앙아시아 |
| **3 (+4개)** | `tl` `si` `bn` `mn` | 필리핀·스리랑카·방글라데시·몽골 |
| 보류 | `ja` `hi` `kk` `lo` | 국내 근로자 수 대비 우선순위 낮음. `kk`는 `ru`로 상당 부분 커버 |

> 이 순위는 법무부 「출입국·외국인정책 통계월보」 국적별 체류자 수로 **착수 전 1회 검증**한다. 30분이면 확인 가능하고, 틀리면 번역비를 통째로 낭비한다.

**언어를 6개로 줄이는 진짜 이유**: 11개를 기계번역으로 깔면 검수를 못 한다. 임금 앱에서 오역은 "야간수당"을 "야간 벌금"으로 만들 수 있다. **6개를 제대로 검수하는 것이 11개를 방치하는 것보다 압도적으로 낫다.**

### 4.2 번역 품질 프로세스

```
1) ko 원문 확정 → 2) en 번역 (기준 언어) → 3) 기계번역 초안 (vi/km/ne/id)
→ 4) 원어민 검수 [필수 게이트] → 5) 릴리즈
```
- 검수 없이 릴리즈된 언어는 UI에 **"번역 검수중" 배지**를 노출하고 en 병기
- 검수 경로: 외국인노동자지원센터, 이주민 지원 NGO, 지역 이주민센터. 협조 요청 시 "임금 체불 대응 도구"라는 목적을 명시하면 협조 가능성이 높다
- 금액·시간·법률 관련 문자열(`legal`, `summary` 네임스페이스)은 **검수 전 배포 금지**

## PART 6. 기술 아키텍처 결정

### 6.1 프론트엔드 (C9)

```
Next.js 15 App Router + TypeScript strict
  → output: 'export' (정적 빌드)
  → 서버 컴포넌트·SSR·API Routes 사용하지 않음
Tailwind CSS v4
Dexie.js (IndexedDB)
zustand (UI 상태만. 영속 데이터는 전부 Dexie)
date-fns + date-fns-tz  ※ Asia/Seoul 고정
PWA: next-pwa 또는 Serwist (앱 셸 프리캐시)
```

**i18n을 next-intl 라우팅으로 하지 않는 이유**
- `/[locale]/...` 구조는 정적 export 시 11개 언어 × 전 페이지를 프리렌더한다 → 번들·빌드 폭증
- 언어 설정이 IndexedDB에 있는데 URL에도 있으면 **두 개의 진실**이 생긴다
- 오프라인 상태에서 언어 변경 시 라우트 이동이 서비스워커 캐시와 충돌

→ **단일 라우트 + 클라이언트 사이드 메시지 동적 import**
```ts
const messages = await import(`@/messages/${locale}.json`)  // 코드 스플리팅 자동
```
`next-intl`은 Provider만 쓰거나, `react-i18next` / 자체 경량 훅으로 대체 가능. **결정: next-intl의 클라이언트 전용 구성 사용** (포맷터·복수형 처리가 검증되어 있음).

### 6.2 폰트 로딩

```
기본:  Pretendard Variable (subset: 한글·라틴·키릴)
km  →  Noto Sans Khmer
ne  →  Noto Sans Devanagari
my  →  Noto Sans Myanmar
th  →  Noto Sans Thai
```
- `<link rel="preload">` 는 **선택된 언어 1종만**. 전체 로드 시 초기 용량이 수 MB로 폭증
- `font-display: swap` + 시스템 폰트 폴백 스택 지정
- 서비스워커에 선택 언어 폰트만 캐시

### 6.3 오프라인 / PWA

| 항목 | 전략 |
|---|---|
| 앱 셸 | 프리캐시 (설치 시) |
| 데이터 | 100% IndexedDB. 네트워크 의존 0 |
| 폰트 | 선택 언어만 런타임 캐시 |
| 업데이트 | 새 버전 감지 시 "업데이트" 토스트, 강제 새로고침 금지 |
| 설치 유도 | 앱 2회 사용 후 1회만 노출, 거부 시 30일 재노출 안 함 |

### 6.4 백엔드 (Phase 2) — 원본 유지 + 보완

Render 무료 플랜 슬립(15분/최대 50초) 대응은 원본대로. 추가 결정:
- 동기화는 **절대 UI를 블로킹하지 않는다.** 실패해도 조용히 재시도 큐에 넣는다
- 충돌 해결 last-write-wins 유지하되, **삭제는 tombstone**으로 처리 (물리 삭제 시 다른 기기에서 부활)
- `POST /sync/push` 요청 크기 제한 1MB, 100건 단위 배치
- 휴대폰+PIN 인증은 SMS 검증이 없으므로 **타인 번호 도용 가능**. Phase 2에서는 "이 번호는 이미 사용중" 정도만 막고, **PIN 5회 실패 15분 잠금 + 복구 수단 없음**을 온보딩에 명시한다. 복구 불가가 곤란하면 SMS(Phase 3) 전까지는 백업 기능 자체를 미루는 것도 선택지다
